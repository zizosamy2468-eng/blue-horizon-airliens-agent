# Final Architecture

## System view

```mermaid
flowchart LR
    User[End user] --> UI[web_platform frontend]
    Admin[Administrator] --> UI
    UI --> API[Flask API]
    API --> Graphs[State-graph agents]
    Graphs --> Runner[StateGraphRunner]
    Runner --> Store[(MySQL workflow runs + checkpoints)]
    Graphs --> MCP[MCP read/write tools]
    Graphs --> RAG[Existing RAG policy corpus]
    Graphs --> Plan[Existing planning modules]
    Runner --> HITL[(admin_tasks)]
    Runner --> Tickets[(failure_tickets)]
    Admin --> API
```

## Durable execution contract

`WorkflowState` is the single payload for a run: it records its ID, graph type, current node, status, workflow data, context, transition history, checkpoint number, waiting reason, administrator task, and last error. `create_run()` writes checkpoint 1. For each `NodeResult`, `StateGraphRunner` moves the state, records the reason, and calls `save_checkpoint()` before it can execute another node.

The runner stops when the status is `waiting_external`, `waiting_admin`, `failed`, `completed`, or `cancelled`. `resume()` loads the saved state by run ID, adds the new event data, persists a resume checkpoint, then continues from the stored node. This is why a process restart cannot re-run already completed nodes.

## Separation of pauses and failures

| Concern | State | Durable record | Resume trigger |
| --- | --- | --- | --- |
| Expected human decision | `waiting_admin` | `admin_tasks` | Admin decision from the platform/API |
| Expected outside response | `waiting_external` | `workflow_runs` + checkpoint | Customer, maintenance, crew, payment, or authority event |
| Unexpected failure | `failed` | `failure_tickets` + workflow state | Ticket is resolved and the actual cause is corrected |

An expected HITL pause must not create a failure ticket. A ticket must identify the node and error and resume from that same stored node after the fix.

## Runtime controls

`state_graph/tool_registry.py` stores per-agent tool permissions in `agent_tool_permissions` and checks them at execution time. The three graph packages call the existing MCP tools and RAG/planning components where those techniques are needed. See [docs/state-graphs.md](docs/state-graphs.md) for individual graph paths and [docs/api-contract.md](docs/api-contract.md) for API boundaries.

## Database ownership

- `workflow_runs` contains the latest durable state for every workflow.
- `workflow_checkpoints` is the immutable transition history.
- `admin_tasks` stores expected approval/review requests.
- `failure_tickets` stores unplanned failures and their resolution metadata.
- Domain tables retain workflow-specific business data: maintenance cases, compensation appeals/revisions, and safety incidents/submissions.
