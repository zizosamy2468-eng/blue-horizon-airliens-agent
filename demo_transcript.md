## 5. Elicitation — Duty-Time Override — [Script]

> **Seed data prerequisite:** update `duty_time_logs` for `crew_id=1` (Capt.
> Karim Mostafa) to `hours_flown = 8.00, hours_on_duty = 14.00` before this
> run — this sits exactly at both daily limits, so the `>=` check in
> `assign_reserve_crew` genuinely fires. (As originally seeded at `7.50` /
> `13.00` this crew member is still under both limits and the tool would
> approve immediately with no elicitation — see the note in `README.md`.)

Run (as the authenticated supervisor session from step 4):
```python
await session.call_tool(
    "assign_reserve_crew",
    arguments={"flight_number": "BH202", "crew_id": 1, "requested_by": "agent_014"},
)
```
The tool reads `duty_time_logs`, finds Capt. Karim Mostafa at the daily
limit, and — instead of rejecting or silently proceeding — calls
`ctx.elicit()`. The `elicitation_callback` in `client_stdio.py` prompts for
`approved` / `supervisor_id` / `note` on the terminal. **[Computed]** — the
message text below is generated by running the tool's own f-string templates
against this seed data, so it's the exact wording the tool will produce, not
a paraphrase:
```
>>> SUPERVISOR APPROVAL NEEDED <<<
Capt. Karim Mostafa has already logged 14.0 duty hours and 8.0 flying hours
today (limits: 14.0h duty / 8.0h flying). Assigning them to flight BH202
would exceed the legal limit. Do you approve this assignment anyway?
approved? (yes/no): yes
supervisor_id: sup_001
note: cleared for one more short-haul sector
```
Approving returns:
```
Approved: Capt. Karim Mostafa (pilot) assigned as reserve crew on flight
BH202. Requested by agent_014. (Supervisor override: Approved by supervisor
sup_001.)
```
Declining (`approved? no`, with a note like "crew fatigued, use a different
reserve") instead returns:
```
Rejected: Rejected by supervisor sup_001: crew fatigued, use a different reserve
```
No row is written to `crew_assignments` until a decision comes back either
way — the call genuinely pauses.

**Control case (no elicitation expected):** the same call with
`"crew_id": 2` (Capt. Laila Hassan, seeded at `4.00` duty / `2.00` flying
hours) should return an `Approved:` result immediately, no elicitation
prompt — useful to show the trigger is conditional, not hardcoded to always
fire.

## 6. Elicitation — Compensation Over Cap — [Script]

```python
await session.call_tool(
    "issue_compensation",
    arguments={
        "passenger_email": "ahmed.samir@example.com",
        "flight_number": "BH202",
        "amount": 750,
        "currency": "USD",
        "reason": "flight cancelled due to mechanical issue",
        "issued_by": "agent_014",
    },
)
```
`750 > MAX_COMPENSATION_WITHOUT_APPROVAL (500)`, so this pauses via
`ctx.elicit()` before any row is inserted into `compensation`. Ahmed Samir is
used here specifically because he has *no* existing compensation record on
`BH202` — Mona Khaled already does (see below), which would trip the
duplicate-payout rejection first and never reach this check. **[Computed]**
exact prompt text:
```
>>> SUPERVISOR APPROVAL NEEDED <<<
Requested compensation of 750 USD for Ahmed Samir (flight BH202) exceeds the
500.0 auto-approve limit. Reason given: flight cancelled due to mechanical
issue. Do you approve this payout?
approved? (yes/no): yes
supervisor_id: sup_001
note:
```
Approved outcome:
```
Approved: 750 USD compensation issued to Ahmed Samir for flight BH202.
Reason: flight cancelled due to mechanical issue. Issued by agent_014.
(Supervisor override: Approved by supervisor sup_001.)
```

**Duplicate-payout rejection (deterministic, no elicitation needed):**
```python
await session.call_tool(
    "issue_compensation",
    arguments={
        "passenger_email": "mona.khaled@example.com",
        "flight_number": "BH202",
        "amount": 100,
        "currency": "USD",
        "reason": "test duplicate",
        "issued_by": "agent_014",
    },
)
```
Mona Khaled already has an `approved` `150.00 USD` compensation record for
`BH202` in the seed data, so this is rejected before the elicitation check
even runs — **[Computed]**:
```
Rejected: passenger Mona Khaled already has a approved compensation of 150.0
for this flight. Duplicate compensation is not allowed.
```

Crew duty-time limit policy (simplified for this project):
- Max flying hours per day: 8 hours
- Max hours on duty per day: 14 hours

## 9. Sampling — [Script]

```python
await session.call_tool(
    "generate_disruption_notice", arguments={"flight_number": "BH202"}
)
```
Inside the tool, `sampling_logic.py` pulls the real disruption reason
("mechanical") from the database, builds a prompt, and calls
`ctx.session.create_message(...)` — a genuine `sampling/createMessage`
request answered by the **connected client's** model, not a model the server
owns. The returned passenger notice text is what the tool hands back.

## 10. Progress Tracking — [Script]

```python
await session.call_tool(
    "rebook_all_passengers_on_flight",
    arguments={
        "old_flight_number": "BH202",
        "new_flight_number": "BH101",
        "requested_by": "agent_014",
    },
)
```
With the current seed data, `BH202` has exactly one `confirmed` booking
(Mona Khaled). For each one, `progress_logic.py` calls
`ctx.report_progress(progress=index, total=total, message="Rebooking <name>
(<index>/<total>)")` before moving that passenger. **[Computed]** exact
output for this seed (total=1, so this also doubles as the minimal case —
worth adding a second confirmed passenger to `BH202` in seed data before the
live demo so the progress bar visibly increments more than once):
```
[progress 1/1] Rebooking Mona Khaled (1/1)
Rebooked 1/1 passengers from BH202 to BH101.
```
Passengers already booked on the target flight are skipped and listed in the
final summary rather than double-booked (none in the current seed data
trigger this path — add a passenger pre-booked on `BH101` to demonstrate it).

**Companion deterministic write test:** `rebook_passenger` on `booking_id=2`
(Mona Khaled, `BH202`→`BH101`) — **[Computed]**:
```
Approved: Mona Khaled rebooked from booking 2 onto flight BH101. Requested by agent_014.
```

**Edge case — empty batch:** running
`rebook_all_passengers_on_flight` on `old_flight_number="BH303"` (its only
booking is already `cancelled`, not `confirmed`) returns:
```
No confirmed bookings found on flight BH303 to rebook.
```
without touching the database — useful to show the tool handles the "nothing
to do" case cleanly rather than erroring.
